- `make build`：后端和前端构建。
- `make test`：后端测试、前端 lint/typecheck 和关键 Vitest。
- `docker compose up -d`：按 Compose 启动服务。
- `go run ./cmd/server`：后端；支持 setup、migration plan/apply、version flags。
- `frontend/package.json`：dev、build、lint:check、typecheck、test:run、coverage。

迁移计划执行前必须确认 catalog/checksum 未漂移；CI、发布、备份恢复和生产健康核验属于受控流程。

发布 worker 的可选 VM 自动启停由 `.ssh.local` 顶层 `vm_lifecycle` 配置，未配置保持旧行为，配置错误 fail-closed；本地检查和全局锁后、首次 VM 连接前检查并无界面启动，以跨 checkout VM 身份锁和持久所有权防止重复使用与崩溃接管。普通 `doctor/status/wait/follow/verify-result` 及插件对应只读命令不自动开关机；`deploy-follow`/`plugin-deploy-follow` 关闭只结束观察，不影响 worker。独立 `vm-validate` 和 VM-only 验证/展示不自动关闭 VM。原本运行的 VM 始终保留，本次启动的 VM 仅在 signed 验真、postdoctor/插件逐实例验收和隔离临时任务清理都成功后 SSH 正常 `poweroff`，再以 `vmrun list` 核实停止；失败或遗留所有权保留 VM，关机失败独立报告 cleanup，不回滚或重发成功发布。公共配置与完整边界见[发布与协调恢复](../03-模块指南/10-发布与协调恢复.md#vm-发布电源合同)。

Sub2API fork 的发布入口由 `sub2api-production-deploy` skill 统一管理：使用完整 commit SHA，按 profile 执行 `doctor`、`deploy-start`/`deploy-follow`、`status`、`wait` 和 `verify-result`。每次发布执行 `fast` 0–2 分钟；恢复相关改动执行 `specialized` 5–15 分钟；`full` 20–60 分钟至少每 30 天演练一次，不阻塞普通发布，但仅恢复算法、备份格式、信任链变化或真实恢复事故修复为生产前硬门禁。候选上线由 `verify-result` 验真，协调恢复由独立 `verify-recovery-result` 验真，两类验真不能互相替代。RackNerd 的发布命令、状态检查、镜像与恢复包传输固定经“DMIT SSH -> WireGuard 地址 1080 HTTP CONNECT -> RackNerd SSH”，使用 10 秒 keepalive，禁止回退到本机代理、旧 8888 或直连。RackNerd 的纯只读 `doctor` 综合探针可在 SSH 连接中断或 `exit_code=-1` 时有限重放；大文件下载与上传均使用 8 个可续传分片、最多 8 条并发连接，每个下载分片使用有界预取。发布写命令出现超时或非零退出时必须先读取结构化状态和 committed marker，不重复启动 runner。fork 差异审计由 `sub2api-fork-extension-audit` 只读执行，报告写入 `.tmp/fork-extension-audit/`。长期合同见[分叉扩展与兼容性](../03-模块指南/05-分叉扩展与兼容性.md)和[发布与协调恢复](../03-模块指南/10-发布与协调恢复.md)。
