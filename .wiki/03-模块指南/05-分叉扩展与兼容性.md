### 上游配置看板扩展

`upstream-config-dashboard` 是 fork 的管理面板扩展：保留真实流量与主动探针分离、配置级收益估算、账号构成和详情抽屉语义。看板聚合查询必须对左连接字段执行 NULL 安全处理，并按 `COALESCE(NULLIF(request_id, ''), id::text)` 去重错误记录。该扩展不新增数据库字段，不改变调度、利润控制、TTFT Guard 或可信度统计。

### 上游渠道余额告警扩展

`upstream-balance-channel-alert` 复用上游配置余额快照、人民币换算证据、`upstream_balance_low_threshold_cny` 和 `balance_low` 事件，为渠道列表及配置看板提供低余额提醒。余额不足只表示“新鲜且成功换算的 `balance_cny` 严格低于正阈值”；快照缺失/过期、解析或换算失败、非正阈值均必须显示余额不可用，不得误报为零余额，也不得读取账号 quota/credits 或站内用户余额。

低余额事件以配置为范围按周期幂等打开，首次跌破阈值通过默认开启的独立开关 `upstream_balance_notify_enabled` 发送一次通知；已配置的有效管理员通知邮箱优先，未配置时自动回退启用中管理员的合法注册邮箱。重复同步不重复发信，恢复关闭事件，再次跌破开启新周期。通知失败不能回滚快照/事件或阻断其它渠道同步。充值入口复用 provider 后台 URL 规则，邮件、事件和日志禁止写入凭据、认证头及原始响应。

### 用户余额不足自动提醒扩展

`user-balance-auto-notify` 在用户余额首次从有效阈值以上跌破阈值时发送邮件。存在已验证且未停用的自定义通知邮箱时，仅发送这些邮箱；没有有效自定义邮箱时自动回退用户注册邮箱。OAuth 历史账号的 `*.invalid` 合成占位邮箱不是可用收件人，界面要求先绑定真实邮箱或验证自定义邮箱。收件人仍经过统一 `EmailService.SendEmail`，因此 QQ 邮箱继承收件域名 SMTP 路由。

迁移 `254_enable_balance_notifications_for_existing_users.sql` 只在发布时将未软删除用户的提醒开关统一开启一次，并为受影响 API Key 写入认证缓存失效 outbox。发布 Gate 必须核对未删除用户转换数量、软删除用户摘要、VM outbox 增量和新版用户认证缓存触发器合同。发布后用户仍可关闭，系统不周期性强制重开。开关、阈值、注册邮箱及自定义邮箱变更必须失效用户 API Key 认证快照，避免计费路径继续使用旧收件规则。
# 分叉扩展与兼容性

本页是 Sub2API fork 相对 `upstream/main` 的长期知识入口。它记录稳定的业务合同、数据边界、运行约束和维护方法，不复制 `.spec/changes/**` 中的一次性 proposal、design、tasks 或测试报告。

## SSOT 与登记边界

- 代码、schema、迁移和测试是行为 SSOT。
- `.agents/skills/sub2api-fork-extension-audit/references/extensions.yaml` 是机器可读的 fork 差异登记 SSOT。
- 本页是面向维护者的长期解释和导航；登记项与本页必须能按扩展 ID 相互核对。
- `.spec/**`、`.wiki/**` 和 `.agents/skills/wiki-*` 是治理/知识资产，不作为 fork 业务扩展路径登记。
- `sub2api-fork-extension-audit` 用于只读审计，`sub2api-production-deploy` 用于发布、恢复和生产门禁；二者的 fork 专属运行合同仍需在本页和对应 skill 中保持一致。

后续流程：

```text
代码或迁移产生 fork 差异
        ↓
更新 extensions.yaml（机器事实）
        ↓
更新本页或对应模块 Wiki（长期解释）
        ↓
运行 audit + spec-wiki-lite validate --strict + diff check
        ↓
在 review/archive 后保留最终稳定合同
```

## 关键运行合同

### 探针、真实流量与调度反馈

可信度配置状态必须区分“缺失”和“显式保存”。只有数据库中存在、JSON 合法且 `enabled=true` 时，OpenAI 才进入 Juice 独立模式：后台探针只看 `LastProbeAt` freshness，不被 `LastEvidenceAt` 抑制；探针收到首字时可将 TTFT 反馈给 OpenAI 调度器，并按原始网络请求结果上报成功/失败。

配置缺失、空值、disabled、读取失败或非法 JSON 统一视为未启用。此时普通后台健康探针沿用真实流量抑制：`max(LastProbeAt, LastEvidenceAt)` 在 freshness 窗口内则跳过。管理员手动探针绕过该抑制。非 OpenAI 可以复用未来的调度反馈接口，但当前不显示可信度徽标，也不使用 OpenAI 专属质量判断。

探针请求的网络结果必须先于 Juice 质量降级保存：

- HTTP/传输错误、超时、取消、流中断、无有效输出：无 TTFT，失败率样本；可信度分母不增加。
- 完整收到响应但 Juice 值错误或 `mixed`：有 TTFT，网络成功率样本；只降低可信度，不改写网络 success。
- `current_success`：有效完成成功样本。
- `unsuccessful`：有返回但答案不正确的有效完成失败样本。

可信度 24h/7d 分数为：

```text
current_success / valid_completed × 100
```

样本不足必须单独标记，不能伪装成 0 分。可信度旧版本（v1）数据不参与新版本统计；清理只清空旧可信度字段，保留同一健康观测中的普通状态、HTTP、TTFT 和时间证据。

### 质量列缓存率

上游管理和账号/分组列表的质量列在 1H、24H 行展示缓存率，位置位于首字/总耗时之后、样本数之前。缓存率只读取成功的真实流式 `usage_logs`（`actual_cost > 0`、`stream = TRUE`），健康探针和 Juice 探针不进入该统计。后端同时返回缓存读取 token（分子）与提示词总量（输入 + 缓存创建 + 缓存读取，分母），前端在 tooltip 中展示两者；分母为 0 时 `cache_rate` 为空，不显示伪造的 0%。

质量分版本为 5：当首字、总耗时和缓存率均有效时使用 50%/15%/35% 权重；缺少缓存率时保持旧版首字/总耗时 85%/15% 语义；仅部分指标有效时按可用权重归一化。版本 5 将缓存创建 Token 纳入缓存率分母，与 Token 使用趋势和 Channel Monitor 的口径一致。质量分仍是只读展示指标，不参与账号调度或计费。

### 渠道监控与主动探针流式化

渠道监控 V1 的 OpenAI Chat/Responses、Grok、Kimi、智谱、DeepSeek、Anthropic 和 Gemini 主动探针默认使用 SSE 流式请求。首字只认首个非空文本增量；`ttft_ms` 保存首字耗时，`latency_ms` 继续保存完整请求耗时。收到首字后断流仍保留 TTFT 但记录失败；空流、HTTP/传输错误和请求自身超时按失败记录。调度器取消（Stop、Unschedule、Schedule 替换）会取消已入队或执行中的请求，不写历史也不推进 `last_checked_at`；管理员手动 `RunCheck` 不受该抑制影响。

`replace` body 明确设置 `stream=false` 时保持非流式 JSON 兼容；缺省 adapter 请求不回退为整包读取。渠道监控历史的 `ttft_ms` 为 nullable，旧历史保持 NULL，不用总耗时回填；V2 被动业务流量聚合和可用率口径不变。上游账号主动探针复用同一增量语义：Grok 使用 Chat SSE，Antigravity 仅主动测试路径使用流式解析，普通业务路径不改变；真实 provider 流式能力在发布验证中标记为 `not_checked`，由隔离 SSE fixture 和代码测试提供证据。

TTFT 的计时起点是每次主动请求调用 HTTP 客户端前的请求开始时间，直到首个非空、非 reasoning、非协议文本增量；响应头前的连接、TLS、排队和等待均计入。首字耗时不足 1ms 时保存为 1ms，未收到可见文本保持 NULL；首字后断流保留 TTFT 但仍记录失败。读取 history、latest、timeline 和立即探测 API 时，旧数据中的 `ttft_ms <= 0` 统一归一为 NULL，不更新历史行。`latency_ms` 始终表示整轮请求（含重试等待）的总耗时，V1 降级只读取总耗时、重试和换号阈值，TTFT 只用于展示。

批量时间线 SQL 的稳定列顺序为 `monitor_id, status, latency_ms, ttft_ms, ping_latency_ms, checked_at`；repository 与 Scan 必须保持同序，确保 `operational/degraded/error` 状态正确到达前端。前端对 NULL/0 TTFT 显示 `-`，总耗时继续单独显示，时间线颜色仍由 status 映射绿/黄/红。

V1 的成功探测降级策略由三个 settings 实时控制：总耗时阈值（默认 6 秒，1–300）、免降级额外重试次数（默认 2，0–4）和免降级累计换号次数（默认 3，0–5）。首次请求不计入重试；重试与换号分别判断，不互相抵扣。最终成功只要任一阈值超限即为 degraded，并保留具体原因；失败、超时、流中断和 challenge 错误仍为失败状态。单监控 `max_probe_attempts` 仍只限制一次探测实际请求上限。

### 管理员用量明细生成 TPS

管理员“使用记录 → 用量明细”的延迟列在首字和总耗时之后展示生成 TPS，Excel 导出同步包含“生成 TPS”。该值表示首个 Token 返回后的文本生成速度，而非包含排队与首字等待的端到端吞吐：

```text
output_tps = output_tokens × 1000 / (duration_ms - first_token_ms)
```

只有 `output_tokens > 0`、`first_token_ms` 存在且 `duration_ms > first_token_ms` 时才返回派生字段 `output_tps`；无首字、无输出 Token、耗时异常以及图片/视频等非文本生成记录均返回空值，前端显示 `-`，不伪造 `0 TPS`。管理员延迟单元格以“首字 / 总耗时 / 输出速率”三行紧凑展示，输出速率保留一位小数并使用 `t/s` 单位；Excel 导出仍直接使用 API 派生值和既有“生成 TPS”字段，不在前端重复计算。

TPS 计算器由用量明细和健康探针共享，避免口径漂移。该字段不持久化、不需要数据库迁移、不支持服务端排序，且不扩展到普通用户用量页。合同回归覆盖 `backend/internal/service/usage_log_test.go`、`backend/internal/handler/dto/mappers_usage_test.go`、`backend/internal/service/upstream_health_probe_client_test.go`、`frontend/src/components/admin/usage/__tests__/UsageTable.spec.ts` 和 `frontend/src/views/admin/__tests__/UsageView.spec.ts`。

### 注册邮箱与 Gmail 普通地址

注册链路保留收件箱身份去重：所有域名去除 `+suffix` 参与查重，Gmail 家族额外去除本地部分点号，并将 `googlemail.com` 折叠为 `gmail.com`。该规则用于防止同一收件箱以不同字面地址重复注册，并由仓储锁与复查覆盖并发创建。

当归一化后的邮箱域名白名单显式包含 `@gmail.com` 或 `@googlemail.com` 时，额外启用 Gmail 普通地址限制：新注册 Gmail 家族本地部分必须匹配 `^[a-z0-9]+$`（大小写归一后判断）。点号变体、`+tag`、下划线、连字符和其它符号在发送注册验证码、普通注册及 OAuth 首次建号前返回 `GMAIL_ALIAS_NOT_ALLOWED`；错误不得包含用户邮箱。白名单为空或不含 Gmail 家族时不启用该额外限制，QQ 与其它域名保持现有规则。

该限制只针对新账号创建，不影响已有账号的密码/OAuth 登录，也不扩展到邮箱绑定。前端注册页与邮箱验证页只做同口径提前提示，后端始终是权威校验。不维护临时邮箱域名黑名单，不调用第三方邮箱信誉服务，不新增字段或 migration。

### 能力、倍率与路由

- 分组利润控制的下游有效倍率为“用户专属倍率（存在时）否则分组默认倍率”，订阅高峰窗口内再乘当前高峰因子；管理端分组列表、编辑弹窗和专属倍率表共用同一预览公式，结果向下保留四位且不参与保存。
- 用户专属倍率允许显式 `0`，而分组默认倍率仍必须大于 `0`。`0` 只对当前用户-计费分组免除余额/订阅消费和利润控制；Token、请求数、`total_cost`、原始成本、账号成本及统计照常记录，`actual_cost/user_spend` 保持为 `0`。API Key 配额、时间窗限速和用户×平台配额使用按分组原价计算的 `quota_meter_cost`，非金额限制和其它用户/分组利润门不变；`nil` 仍表示回退分组默认倍率。
- 图片能力、图片成本和视频成本均以 Key 快照及 effective multiplier 为依据，未知/过期/部分数据不得显示为免费。
- `video_rate_independent=true` 时，必须存在合法 `video_rate_multiplier`；缺失或无效时 `supported=false`。
- `prefer_lowest`/`strict_lowest` 只能在健康、共享并发、TTFT Guard 和 Priority 约束通过后进行成本排序。
- 精确 effective rate 贯穿 Key、派生账号、图片成本、scheduler metadata、调度日志和未来 usage 快照；历史 usage 不回算。

### 用户活动与独立邀请抽奖

每日活动是 fork 的独立奖励扩展，不复用外部活动页面接口、脚本或 token，也不把活动奖励混入现有邀请返利。充值成功结算、真实消费结算和邀请达标事件先按活动日/事件去重；失败、取消、退款和管理员赠送不进入充值门槛，显式用户专属倍率 0 的消费不增加消费抽奖进度。

每日礼包按 `Asia/Shanghai` 活动日每用户最多一次；充值/消费进度每日重置，抽奖机会、邀请达标计数和奖励历史永久保留。被邀请用户累计成功充值达到 10 元时，按 `(inviter_id, invitee_id)` 只产生一次达标计数；每 5 个达标邀请生成一个永久邀请抽奖机会，奖励区间为 5～10 元。充值抽奖和消费抽奖默认每满 50 元产生机会，默认奖励区间为 0.50～1.00 元。

用户接口只接受活动类型、数量和幂等键，身份来自认证上下文；门槛、可用机会、奖励金额、随机结果和规则版本由后端计算。抽奖事务锁定机会、生成整数分/Decimal 奖励、写入独立活动账本并通过统一余额服务入账，唯一约束与幂等键防止重复发放。管理员配置受后端硬上限和审计约束，历史奖励保留生效规则版本，不因后续配置变化重算。

## 后续维护规则

每次 fork 新增或修改与 `upstream/main` 不同的行为时，必须完成以下闭环：

1. 在 `extensions.yaml` 新增或更新唯一扩展 ID、路径、符号、迁移、测试和 invariants。
2. 在本页对应章节补充长期合同；若已有模块页覆盖，则更新模块页并在本页总览中保留入口。
3. 不登记 `.spec/**`、`.wiki/**` 或 `.agents/skills/wiki-*`；这些是治理和知识资产。
4. 运行 fork audit、`spec-wiki-lite validate --strict`、相关测试和 `git diff --check`。
5. 只有实现完成并通过 review/archive 后，才把仍有长期价值的事实保留在 `.wiki`；过程性证据留在 `.spec`/archive。
6. upstream 合并前后重新核对 `upstream/main` SHA、migration checksum、生成文件漂移和本页覆盖情况；不得用删除 Wiki 记录来掩盖未登记业务差异。

## Skill 合同映射

### `sub2api-fork-extension-audit`

- 只读检查，不执行 fetch、merge、checkout、reset、代码生成、构建、VM Gate 或生产操作。
- 审计必须使用操作者提供的 40 位官方目标 SHA；短 SHA、未知对象、脏工作区、冲突和 catalog 不可读均为 blocker。
- `extensions.yaml` 是唯一机器可读事实源；报告只写 `.tmp/fork-extension-audit/`。
- `catalog_update_required` 不能通过扩大通配符隐藏，必须补齐扩展 ID、路径、迁移、invariants 和最低测试。
- 高风险冲突不得用整文件 ours/theirs 解决；官方修复覆盖关系按故障域分别判断。

### `sub2api-production-deploy`

- Fork 版本严格为官方 `VERSION` 加 `-baiyu`；fork VERSION 每变化一次都新增下一个连续整数 profile，parent 指向此前当前 profile，即使无新增 migration 也创建 `new_migrations=[]` 的新 profile；历史 profile、migration、checksum 和 compatibility identity 不回写。profile 242–244 分别固定对应 `0.1.183-baiyu`、`0.1.184-baiyu`、`0.1.185-baiyu`；官方 `0.2.0` 合并使用 profile 245 与 fork 版本 `0.2.0-baiyu`。
- 官方 migration 编号若与 fork 已发布历史冲突，必须保留 SQL 内容并改用下一段本地连续编号。本次官方 `232/233` 四个 migration 重编号为 `256–259`；当前 profile 245 另追加 fork migration `260_daily_activity_rewards.sql`。`255_account_proxy_bindings.sql` 仅作为已发布兼容残留保留，回退后的代码不重新依赖该表。
- 后端、数据库、fork、共享契约和配置改动必须走 `sub2api-dev` VM Gate；本机静态/unit 检查不能替代正式 Gate。
- 正常应用发布使用 active/candidate 双槽和 graceful reload；旧容器在候选构建、传输和验证完成前保持运行，排空超时优先回切旧槽。
- 一个 release 只允许一个 runner、一个 active claim 和一个 candidate；异常、超时或断连先按 committed marker 和结构化状态 reconciliation，禁止重复 deploy。
- 生产清理和备份清理均先 dry-run，再用同一 `plan_sha256` apply；禁止扩大删除范围。
- 生产原始 stdout/stderr 与容器日志只保存在 release 目录 root-only 文件，不复制到 `.tmp`、控制台或最终报告。
- preflight 必须同时核对整体 profile 与单个 migration 状态（`absent/verified/unknown`）；checksum 或语义不一致立即停止。
- Gate v2 当前 profile（现为 245）的升级合同是 health-only；历史 profile 242–244 仅保留用于受控恢复/审计。只验证容器 health、应用 `/health` 和路由，不读取账号池、不发送模型请求、不生成 usage attribution。
- 正式成功必须同时具备签名 Gate、`production-result.json` verified、`verify-result` 通过和 post-deploy doctor 通过；否则只能进入 reconciliation。

这两套 skill 的稳定边界需要同步反映到本页；过程命令、单次 release ID、临时日志和测试输出仍留在 `.spec`、`.tmp` 或受控 release 目录，不写入长期 Wiki。
