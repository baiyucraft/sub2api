## 上游整体评价口径

上游配置看板以配置为聚合主体，不把单个上游账号的健康状态直接等同于配置整体状态。真实业务流量用于请求量、成功率、错误和收益；主动探针用于无流量时的健康补充，两者不混入普通成功率、收入或成本。详情接口提供趋势、模型、最近错误、账号构成和探针可信度摘要。

收入使用下游实际计费字段；只有上游成本及人民币换算率完整时才计算估算毛利，否则显示估算不可用，避免输出误导性收益。

## 用户专属倍率与双金额计费

分组默认倍率仍必须为正数；用户-分组专属倍率支持 `nil`、正数和显式 `0` 三种状态。`nil` 表示回退分组默认倍率，正数按专属倍率计费，`0` 表示该用户在该分组免除余额/订阅消费，并只对当前用户与当前计费分组生效。

显式 `0` 不会丢弃业务用量：`usage_logs` 的 Token、请求数、`total_cost`、原始成本、账号成本和模型/渠道/分组统计仍按原口径记录；`actual_cost` 与用户余额/订阅用量保持为 `0`。API Key 配额、时间窗限速和用户×平台配额使用独立的 `quota_meter_cost`，按分组默认倍率、高峰倍率及图片/视频/搜索/音频的原有计费规则计量，因此金额限额仍然有效。余额不足通知只依据用户实际费用，不会由 0 倍率请求触发。

资格检查对显式 `0` 跳过余额不足和订阅金额日/周/月限额，但仍检查订阅有效期；API Key 配额、RPM、并发、模型能力、账号状态等非金额限制不变。利润控制只对该用户-分组组合豁免，其他用户、其他分组和实际切换后的计费分组继续执行原利润门。倍率更新会失效本地解析缓存和 API Key 认证快照，避免旧专属倍率继续生效。

## 渠道监控停机与刷新边界

V1 主动探针的生命周期与真实渠道状态分开管理。进程收到停机信号后，先让渠道监控 runner 进入 quiesce：取消定时任务、禁止新探测提交；在途请求因 runner task context 取消而不写入历史，也不推进 `last_checked_at`，最终由应用 cleanup 等待并 drain worker。普通运行期的 HTTP、网络和超时错误仍按原规则记录为失败，不得被静默。

启动时加载的存量监控首轮探测延迟 5 秒，给 HTTP 服务监听和路由切换留出缓冲；新建、编辑或启用监控通过 CRUD `Schedule` 仍立即探测。用户端 V1 自动刷新请求失败只代表页面暂时无法更新，保留最近一次真实卡片状态、颜色和时间线且不弹红色错误；手动刷新失败仍提示用户但不清空已有数据。
# 网关与上游

网关经过 API Key 鉴权、用户/组策略、并发与速率限制、账号/渠道调度后转发到 provider。账号、group、channel 保存资源、代理、定价、健康和调度权重；gateway service 处理协议兼容、流式输出、用量、计费和错误映射；adapter/probe 负责 provider-specific auth、模型和健康证据。

普通账号可以通过 `account_proxy_bindings` 有序绑定多个代理。账号的 `Concurrency` 会作为每个代理路由的独立上限，例如账号并发为 5、绑定两个代理时形成两个独立的 `account_proxy:{account_id}:{proxy_id}` 容量池，总容量为 10，但数据库中仍只有一个账号。调度先沿用账号优先级、倍率、模型能力和健康过滤，再在该账号的可用代理中按实时负载选择；停用、过期或软删除代理保留绑定记录但不参与请求。`accounts.proxy_id` 与 DTO 的 `proxy_id/proxy` 始终表示首选代理，供旧客户端和后台刷新/探测兼容。

流式响应开始输出后不应透明切换账号；错误映射和 failover 资格需同时核对 handler、service、adapter 和 focused tests。

本 fork 的上游配置、派生账号生命周期、模型能力同步、健康探针、Juice 可信度、TTFT 调度反馈、精确倍率和图片/视频能力判断，统一见[分叉扩展与兼容性](./05-分叉扩展与兼容性.md)。其中：

- 后台探针是否受真实流量抑制，取决于可信度配置是否“显式存在且 `enabled=true`”；
- OpenAI Juice 只统计有效完成响应，网络异常不进入可信度分母；
- 视频支持必须有有效 effective video multiplier，不能只凭能力开关字段判断；
- 上游派生账号编辑继续执行白名单和 OpenAI 专用类型校验。

## 上游配置整体看板

管理端按 `upstream_config_id` 汇总真实流量、主动探针和账号池，二者必须分栏：探针样本不计入真实请求量、收入、成本或普通成功率；真实流量不足时只能作为健康补充。看板收益字段始终标注为估算，缺少成本、收入或统一币种时显示不可用，不将 `actual_cost` 直接解释为净利润。TTFT 与完整总耗时分别展示，状态判定沿用既有健康阈值，不改变账号调度、利润控制或 TTFT Guard。

## 上游渠道余额告警

渠道余额的唯一来源是上游配置的余额快照及其人民币换算证据，不读取上游账号的 quota/credits，也不读取站内用户余额。读取层以最近 24 小时作为余额快照新鲜窗口；只有快照新鲜、余额解析成功、币种换算完整且 `upstream_balance_low_threshold_cny` 为正时才进行阈值判断；`balance_cny < threshold_cny` 才算余额不足，等于阈值不告警。

缺失/过期快照、解析失败、换算率缺失或非正阈值统一显示“余额不可用”及原因，不能伪造为 `0` 或低余额。现有 `balance_low` 事件按“上游配置 + 一次低余额周期”幂等打开：首次跌破阈值通知一次，重复同步不重复发信，余额恢复时关闭事件，恢复后再次跌破才开启新的通知周期。通知使用独立的 `upstream_balance_notify_enabled` 开关，设置缺失时默认开启；存在已验证且未停用的管理员通知邮箱时优先使用，否则自动回退到所有启用中管理员的合法注册邮箱。通知故障不阻塞快照或事件落库。

渠道列表、上游看板卡片和详情必须使用同一余额/阈值/更新时间口径；低余额渠道可通过现有 provider 后台 URL 入口定位充值。邮件、事件和日志只允许渠道名称、Provider、余额、阈值、更新时间、不可用原因和脱敏后台链接，禁止写入 Key、Token、Cookie、认证头或原始上游响应。
