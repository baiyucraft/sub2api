# 用户活动与奖励

用户活动是独立于邀请返利的奖励域。页面可以展示进度和操作入口，但门槛、次数、奖励金额、随机结果和余额入账均以服务端为准；浏览器提交的金额、倍率、用户 ID 或中奖结果不属于可信输入。

## 首期规则

- 每日礼包：按 `Asia/Shanghai` 活动日统计成功充值，累计满 $10，每日每用户最多领取一次，奖励 $0～0.50。
- 充值抽奖：当日成功充值每满 $50 产生一个永久机会，每次奖励 $0.50～1.00。
- 消费抽奖：当日成功消费每满 $50 产生一个永久机会，每次奖励 $0.50～1.00。显式用户专属倍率为 0 的请求不增加消费进度，但仍按现有口径记录其它用量/成本。
- 邀请达标抽奖：被邀请用户累计成功充值达到 $10 时，邀请人计一次；同一被邀请用户只计一次。累计 5 次产生一个永久机会，每次奖励 $5～10。

上述数值为默认规则，实际使用管理员当前配置；余额、奖励和成本沿用系统已有 `$` 口径，不做汇率换算。

活动充值来源与邀请返利采用相同口径：成功完成的余额订单、成功完成的订阅订单、正数余额兑换码，以及“管理员充值参与邀请返利”开关开启时发生的正数 `add` 加款。支付履约自动生成并兑换的余额码只按订单计一次；管理员 `set`/`subtract`、失败/取消/退款订单、并发码、订阅码和负数余额码不计入。管理员 add 的资格按发生时的开关写入独立幂等事件，不能用历史正数 admin_balance 流水猜测。每日充值/消费进度随中国时区日界线清零，抽奖机会、邀请达标计数和奖励历史永久保留。活动启用前的历史数据不追溯发奖。

每日充值礼包和充值抽奖卡片均提供“去充值”入口，统一跳转现有 `/recharge-store` 充值商城；活动页不自行创建订单或复制商城支付逻辑。

## 与邀请返利的边界

活动达标计数、活动机会和活动奖励使用独立账本。现有 `AffiliateService` 继续负责邀请返利、冻结和转余额；活动奖励不能增加返利配额、返利冻结额或返利流水。用户可以同时看到两套记录，但它们的金额和资格不能互相推导。

## 后端权威结算

用户接口只从认证上下文获取用户身份：summary、奖励历史、礼包领取和抽奖动作均不接受客户端金额或目标用户 ID。抽奖请求只允许活动类型和数量，服务端根据当前规则版本读取可用机会，在事务中锁定并消费机会，使用安全随机源生成整数分/Decimal 奖励，写入可审计奖励记录、更新有效用户余额并记入成本。

礼包的“每日一次”、机会的“一次消费”和邀请对象的“一次达标”必须由数据库唯一约束及幂等键共同保证。支付 webhook、履约重试和异步消费事件先经过事件去重，再更新活动进度；余额入账失败不得留下可再次消费的半完成奖励。

管理员配置只允许在系统设置中修改，并由后端校验门槛、奖励上下限、邀请次数和硬上限。奖励记录保留生效规则版本，后续改配置不重算历史奖励。日志和审计只允许记录活动类型、规则版本、金额分、状态和脱敏用户引用，不记录 token、完整请求体或外部页面凭据。

## 管理员追溯与成本

用户列表的“领奖记录”打开“用户资金与权益变动记录”并预选活动领奖；用量页复用相同弹窗。`GET /admin/users/:id/balance-history` 的全部类型混排兑换、返利转余额和 `credited` 活动奖励，`type=activity_reward` 单独筛选奖励。响应保留旧流水字段，追加 `record_source`、`source_id`、`activity_type`、`period_date` 和独立全历史 `total_rewarded`；零金额奖励也保留。`total_recharged` 保持原正数余额充值口径。发生时间降序、来源升序、原始 ID 降序保证同时间顺序稳定；前端使用来源与原始 ID 的组合键。

四类奖励各对应一条 `extra_cost_entries.category=activity_reward` 自动流水。`activity_reward_id` 唯一，`related_user_id` 与 `activity_type` 保存审计快照；关联不使用外键级联，以免用户删除丢失成本。金额直接从奖励表 NUMERIC 复制，成本时间保留奖励 `created_at`，日期为该时间对应的北京时间自然日。历史机会今天领取计入今天，不按机会所属日期记账。

奖励、机会消费、用户余额和成本在同一事务提交，任一步失败均回滚；不存在或已软删除的余额接收方也不能提交。幂等重试校验全部来源快照，已有冲突关闭事务，成功提交后才失效余额与管理员统计缓存。自动成本不接受人工新增或冲正，`activity-reward:` 幂等键前缀保留给自动账本。现有今日成本、累计成本、趋势和全站用量汇总继续统一聚合额外成本。

迁移 `289_activity_reward_costs.sql` 创建关联字段与补录函数 `backfill_activity_reward_costs()`，补齐全部历史 `credited` 奖励，不重复增加余额。重复执行仅补缺失记录并核验已有快照，保留原日期和人工成本。发布使用连续 profile 264 数据库门禁；旧实例排空后再次显式补录并逐日核对数量、金额，覆盖切换期间旧实例产生的奖励。维护脚本 `backfill-activity-reward-costs.sh` 默认只读 check，apply 要求明确确认旧实例排空；独立维护仍须生产授权。

已授权的 profile 264 停机发布在迁移完成、全部旧实例退出、新进程启动之前，由签名 helper 执行 check → apply → check，任何孤立/快照不匹配或数据库错误均阻断。随后使用同一候选的 `--clear-dashboard-cache` 清除配置对应的单个 Redis dashboard snapshot 并核验缺失，新进程启动重建本地统计缓存。该维护模式不启动应用后台、不迁移、不清理其他 Redis 键；三个对账结果与缓存刷新结果保存在 release 的 root-only state。在线补账仍需显式 catch-up 和缓存重建，不等待 TTL，也不造成本记录触发刷新。

## 维护入口

- 过程 change：`.spec/changes/daily-activity-rewards/`
- 管理员追溯与成本 change：`.spec/changes/admin-activity-reward-history-and-cost-ledger/`
- 用户页面：`/activities/daily`
- 现有邀请返利：`frontend/src/views/user/AffiliateView.vue`、`backend/internal/service/affiliate_service.go`
- 充值履约：`backend/internal/service/payment_fulfillment.go`

修改活动规则、账本或接口时，必须同步更新 SpecWiki change、后端单元/集成测试和本页长期合同，并运行 strict validate、类型检查、Lint 与差异检查。
