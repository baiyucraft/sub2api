# 发布与协调恢复

本页记录 Sub2API fork 的稳定发布与恢复合同。执行细节、单次 release ID、临时日志和现场输出由 `sub2api-production-deploy` skill、`.tmp` 与生产 root-only release 目录管理，不写入 Wiki。

## 三层门禁

| 层级 | 预计额外时间 | 触发范围 | 阻塞规则 |
| --- | --- | --- | --- |
| `fast` | 0–2 分钟 | 每次应用、插件和运维资产发布 | 必须通过 |
| `specialized` | 5–15 分钟 | migration、PG/Redis、Compose、备份、restore/cleanup/reconcile、ingress 或发布状态机变化 | 对命中范围必须通过 |
| `full` | 20–60 分钟 | 定期真实灾备演练；恢复链重大变化或真实事故修复 | 不阻塞普通发布；恢复链自身变化时是生产前硬门禁 |

时间是计划预算，不是强制超时。runner 是否继续只由结构化阶段、命令自身 timeout 和进程状态决定。`fast`、`specialized`、`full` 是叠加关系，不替代变更分类、VM Gate、签名 Gate、备份、迁移和生产验收。

`full` 建议至少每 30 天执行一次，记录上次时间、下次到期时间和实测 RTO。逾期对普通发布只告警；恢复链、备份格式或恢复信任链变化时，未通过当次 `full` 不得进入生产。

默认发布使用 `--recovery-gate-mode auto`，根据生产完整 commit、最终 diff 和 pending migration 自动选择 `fast` 或 `specialized`。需要显式执行完整门禁的 VM 恢复部分时使用：

```text
python .agents/skills/sub2api-production-deploy/scripts/release.py deploy-follow --profile <profile> --commit <40位完整SHA> --mode blue-green|downtime --recovery-gate-mode full --lang zh-CN
```

该参数只绑定 `full` 分类并执行真实生产恢复包、旧镜像和隔离恢复检查，不表示生产级灾备故障注入、独立 `drill_id`、RTO 测量和演练收口已经完成；完整演练仍是单独的运维流程。

## Specialized 故障注入

恢复相关改动至少覆盖：

- Redis 健康时间超过 60 秒但在恢复预算内成功。
- Redis 惰性过期造成总键与 TTL 键不同步下降。
- 核心恢复完成后在 cleanup 前中断，并只续跑收口。
- `recovery_restored` 与过期 ingress `applied` marker 并存。
- 新 orchestrator 拒绝调用事故 release 内的旧 helper。
- 已完成 checkpoint 重放不重复恢复 PostgreSQL 或 Redis。

## Redis 恢复不变量

Redis 惰性过期使用单调不等式验收：

```text
restored_dbsize <= backup_dbsize
restored_expiring_keys <= backup_expiring_keys
restored_permanent_keys >= backup_permanent_keys
```

这些不等式不能替代 checksum、RDB/AOF 完整性、认证来源、Redis 启动、`PING` 和 keyspace 可读性。任何永久键减少都必须 fail-closed。

## Helper 原子版本

恢复 orchestrator、restore、cleanup 和 reconcile 是一个原子 helper bundle。manifest、runner 状态与最终报告绑定完整 commit 和 `recovery_helper_bundle_sha256`。历史 release 内 helper 只作事故证据，不得被新版 supervisor 调用，也不得被删除或覆盖。

## 幂等 checkpoint

协调恢复按以下语义阶段保存 checkpoint：

```text
postgres_restored
redis_restored
compose_restored
app_healthy
nginx_restored
backup_units_restored
claim_reconciled
state_cleanup
```

断线或进程退出后先复核现场。满足不变量的阶段直接跳过，状态矛盾则 fail-closed。业务已经恢复、只剩 cleanup 时，不得再次恢复数据库。

## 验真边界

- `verify-result` 只证明 signed candidate 成为生产运行版本。
- `verify-recovery-result` 只证明恢复点绑定的旧版本、PostgreSQL/Redis、Compose、入口、backup units、claim 和恢复 marker 已完成收口。
- 两类验真不可互相替代，不能修改状态或放宽 `verify-result` 使其接受 recovered release。
- 两类验真之后都必须执行匹配完整 SHA/profile 的 post-operation `doctor`。

## 长期证据

发布或演练报告至少记录门禁层级、触发原因、预计/实际耗时、helper bundle SHA-256、最后 checkpoint、完整演练到期状态、实测 RTO 和脱敏结果。原始 stdout/stderr、凭据、数据库内容和解密材料不得进入 Wiki 或最终报告。
