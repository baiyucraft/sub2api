# 发布与协调恢复

本页记录 Sub2API fork 的稳定发布与恢复合同。执行细节、单次 release ID、临时日志和现场输出由 `sub2api-production-deploy` skill、`.tmp` 与生产 root-only release 目录管理，不写入 Wiki。

## VM 迁移计划的来源边界

Gate v2 的 `plan-before.json` 始终来自签名 manifest 绑定的生产 snapshot，用于生产待迁移与 Gate 对外证据。`plan-actual.json` 来自隔离 probe 数据库，用于 VM 的迁移 hooks、absent/existing 判定和精确计划执行。两份计划及迁移后计划均须校验 catalog、checksum policy、已执行校验和及冲突/未知项；迁移后必须零 pending。

`fast` 从 VM 开发库复制隔离 probe，允许该库落后于生产，但生产 snapshot 必须零 pending。通过严格校验完整实际计划后，只在一次性 clone 中执行 fixture bootstrap，保留独立 before/apply-exit/after 证据；after 必须零 pending，再运行 verified preflight/postflight/semantics。此 bootstrap 不是生产迁移前置证据，不给尚缺依赖表的后继迁移伪造 absent preflight。`specialized/full` 从生产恢复包建立 probe，继续要求生产与 probe 待迁移 filename/checksum 一致。VM 补迁移不写入生产 pending，不得把 fast 的开发库验证记录为生产恢复已验证。任何失败保留原 release 证据，后续修复使用新提交和新 Gate。

## 备份密钥自动准备

已明确授权的发布、停机部署或恢复演练包含本次新备份加密 identity 的自动准备。执行器优先复用已登记且权限与 recipient 指纹合格的专用 identity；缺失时自行生成唯一版本的 age X25519 identity，选择工作区外的用户专属持久安全存储，完成权限、加解密自检和指纹登记，不再要求用户提供私钥、确认生成或指定路径。

执行入口为 `python -m release.backup_keys`（从仓库根设置技能 scripts 的 `PYTHONPATH`）；自动选择持久存储、准备固定版本工具、核验 ACL/owner/mode、生成或复用身份并完成加解密自检。普通停机回退使用经过校验的临时明文恢复包。真实加密灾备验证和版本基线晋升使用新 key 加密的新建备份，仍须实际恢复 PostgreSQL/Redis、完整 Compose/config、旧 image，完成故障续跑、独立审阅、既有信任根签名与原子晋升。密钥自检不证明真实恢复。

私钥不进入生产机、DMIT、备份机、Git、`.tmp` 或日志；隔离 Guest 仅使用受控副本，持久主副本与一次性 Guest/VM 生命周期分离。Linux 验证 `0700/0600` 和 owner，Windows 验证显式 ACL；拒绝链接、覆盖旧 key 和不安全父目录。新资产绑定 key 版本与 recipient 指纹，证据只含指纹和白名单状态。

新生成 key 无法解密旧密文；旧 key 缺失时保留旧资产并报告历史恢复能力缺口，为当前发布新建备份继续验证，不改写旧 manifest。旧 verified 指针与旧 key 在新基线晋升前保留，之后仍按资产引用和 retention 管理。自动生成不包含 Gate/DR Ed25519 签名信任根轮换或既有 daily recipient 切换。完整操作规则见 [备份与灾备恢复](../../.agents/skills/sub2api-production-deploy/references/backup-and-restore.md#备份密钥自动准备)。

### 执行器决策边界

下列事项属于已授权发布或恢复演练的执行准备，由 runner 自动完成，不向用户提出路径、私钥或“是否生成”的问题：

| 情况 | 执行器动作 | 对外证据 |
| --- | --- | --- |
| 存在权限、工具版本和 recipient 指纹均匹配的专用 identity | 复用并重新执行权限与加解密自检，用公开 recipient 创建本次新资产 | 只记录 key 版本、指纹和密钥自检通过状态 |
| 本次需新建加密资产且没有可复用的合格 identity | 在工作区外的用户专属安全存储中独占生成新的 age X25519 identity，并用公开 recipient 创建新资产 | 记录生成/保管/自检结果，不暴露私钥或路径 |
| 需要恢复旧密文但原 identity 缺失 | 保留旧密文、manifest 和失败证据；不得用新 key 冒充匹配 key | 明确标记历史恢复能力缺口，当前发布仍可按新资产继续验证 |
| 自动准备、加解密自检或真实恢复失败 | 处理授权范围内的环境问题，保留失败证据并停止对应门禁 | 报告固定失败分类，不请求用户补交密钥来绕过门禁 |

自动生成的备份 identity 与 VM Gate/DR 的 Ed25519 信任根分离管理；执行器不得借此替换签名根、改写旧证据或把 key 自检升级为 full DR 通过。

### 隔离恢复临时文件权限

Guest 恢复服务使用 `UMask=0077`，入口在处理私钥或明文前主动固定进程掩码为 `0077`；解密子进程也显式使用该掩码。解密输出从创建时即为 `0600`，不依赖宿主或 systemd 默认值，不以事后 `chmod` 替代安全创建。来源验证继续只接受 `0400/0600` 的普通单链接文件；权限检查失败保留原失败证据，不放宽校验或在旧 drill 内重跑。修改这些 helper 字节后必须使用新提交、新 helper 闭包、新授权和新 drill，重新完成真实恢复门禁。

隔离 Guest 的签名 helper 校验必须使用 `python3 -B -I`。`-I` 会隔离解释器环境，不能依赖 `PYTHONDONTWRITEBYTECODE` 阻止 `__pycache__`；若验签脚本在 helper 目录写入 `.pyc`，后续 `recovery_bundle.py --verify` 会因目录 inventory 漂移而 fail-closed。该参数约束同时适用于授权 envelope 校验和 drill authorization 校验，并应由回归验证 helper 目录在验签前后保持同一文件集合。

### Guest 内嵌 Docker 的同类故障归因

离线 `systemd-nspawn --private-users=pick` Guest 内再启动 Docker 时，runc 可能在创建容器前报 `unable to join session keyring: ... operation not permitted`。宿主随后只看到 `guest-measurements.json` 缺失，这只是二次症状；先读取 Guest 的阶段 marker 与 `helpers.raw.log`，确认是否停在 `guest_prepare_system`，再决定修复范围。

隔离 Guest 的 `daemon.json` 使用自定义 `runc-no-keyring` runtime 作为默认 runtime。启用 containerd snapshotter 时，Docker 走 `io.containerd.runc.v2` shim；必须在 runtime 的 `options` 中设置 `NoNewKeyring: true`。把 `--no-new-keyring` 放进 `runtimeArgs` 会在 shim 层被当成错误的顶层 runc 参数，容器启动仍会失败。Docker 的内置 `runc` 名称是保留名，直接在 `runtimes` 中重定义会导致 daemon 报 `runtime name 'runc' is reserved`。该设置只作用于一次性恢复 Guest，不修改宿主 Docker daemon。Guest 启动前还会移除 nginx 与 systemd-resolved 的自动启用链接：nginx 要等归档配置恢复后再启动，private network 没有可用 DNS。任何 helper 字节变化都必须重新构建 bundle、生成新 drill、扫描历史 drill 的同类错误并保留失败证据，不能在原 drill 内重跑或用缺失测量文件继续 Gate。

移除这些链接时必须按 Guest rootfs 解释目标：systemd 常见的绝对链接 `/lib/systemd/system/<unit>` 要映射为 `<rootfs>/lib/systemd/system/<unit>`，不能直接调用宿主侧 `Path.resolve()`。后者会把合法 Guest unit 看成宿主文件系统中的 dangling link，并在 Guest 启动前错误阻断 Full DR。实现必须拒绝解析后越出 rootfs 的相对链接，并同时要求目标是普通文件且 basename 与链接名一致；该边界应由绝对链接成功和 rootfs 越界失败两类回归覆盖。

## VM 发布电源合同

可选 `.ssh.local` 顶层 `vm_lifecycle` 是主机运维配置，与 `servers` 并列；公共字段如下，不包含连接秘密：

```yaml
vm_lifecycle:
  enabled: true
  vmrun_path: 'C:/MProgram/VMware/vmrun.exe'
  vmx_path: 'D:/vmu/Ubuntu.vmx'
  startup_timeout_seconds: 180
  shutdown_timeout_seconds: 180
```

未配置保持旧行为；配置错误、VM 身份或电源状态无法证明时 fail-closed。后台应用/独立插件发布 worker 在本地检查和发布全局锁后、首次 VM SSH/API 连接前，取得跨 checkout 的规范化 VM 身份锁并核对持久所有权，以 `vmrun list` 检查电源；仅对已停止目标使用 `vmrun start <vmx> nogui`，有界等待 SSH 就绪。

VM 原本运行时始终保留，`vm_started_by_release=false`。本次启动必须持久记录 VM、release、完整 commit、worker 进程启动身份、初始电源与阶段；启动意图先于启机落盘。崩溃释放进程锁不等于所有权可接管，遗留、冲突或不完整记录阻断后续发布，不自动删除、覆盖或代为关机。
正常收口持久记录完成结果并结束本次活动所有权，保留审计证据；本次启动须先核实停止，原本运行则记录保留。明确完成的历史记录不属于待接管所有权，失败或不明记录不得伪装成完成。

只有本次发布启动且所有权仍一致，才在 signed 应用验真与 post-deploy doctor（插件为 signed 验真及逐实例版本、binary SHA、Health、受管范围验收）和本 release VM 隔离临时任务清理全部成功后，通过 SSH 正常 `poweroff`，再于关机 timeout 内用 `vmrun list` 核实停止。VMware Tools 不是依赖，禁止 hard 关机；SSH 断开不能代替停止证明。持久数据、展示、回滚 image、Gate、marker 和失败证据不属于临时清理范围。

失败、blocked、恢复旧版本或崩溃保留 VM 与所有权。清理/关机/停止核实失败独立记录 cleanup 失败，保留成功生产发布事实，不回滚、不重发、不重跑迁移或重复插件升级。状态白名单增加 `vm_power_status`、`vm_started_by_release`、`vm_cleanup_status`，禁止输出完整所有权、VMX 路径或原始回包。

普通 `doctor/status/wait/follow/verify-result` 及插件对应只读入口不自动开关机；VM 已停止时普通 doctor 的 Guest 检查会失败。worker 的 postdoctor 在关机之前完成。独立 `vm-validate`、VM-only 验证/展示不自动关闭 VM 或持久展示容器。观察器关闭、超时或 Ctrl+C 不影响后台 worker、锁和所有权。执行细节见 [release-runner-lifecycle.md](../../.agents/skills/sub2api-production-deploy/references/release-runner-lifecycle.md)。

### VM 迁移前置检查失败的租约收口

`reconcile-vm-preserve --failed-stage migration-preflight` 是独立于 pre-validator/candidate-build 的受限证明入口。它只接受冻结的 profile 273 helper 提交中迁移 298 的已知前置约束误判，绑定原 manifest SHA、validator/assertion 字节、失败阶段/行号、hook、before/actual plan 及已完成 hook 集合。必须证明迁移尚未 apply、无后续 Gate 或候选归档、原隔离 probe 已清理、原 worker 已退出、同 VM boot/owner，且生产 release/claim 不存在、旧镜像和备份健康。

入口持发布与 VM 身份锁，远端核验发布单元/Gate 锁及文件 owner、mode、单链接和描述符 inode，拒绝在途验证器、构建或恢复任务；第二次完整复验后保存独立 preserve 证明，最后提交 shared owner 的 released 标记。原 failed 状态、manifest、日志和 VM 电源保持原样。新提交或其他阶段不得借用该事故分支；重新发布使用新 commit、candidate、Gate 和 release，helper 变化后重新分类并完成要求的真实恢复及签名。

## 三层门禁

| 层级 | 预计额外时间 | 触发范围 | 阻塞规则 |
| --- | --- | --- | --- |
| `fast` | 0–2 分钟 | 每次应用、插件和运维资产发布 | 必须通过 |
| `specialized` | 5–15 分钟 | migration、PG/Redis、Compose、备份、restore/cleanup/reconcile、ingress 或发布状态机变化 | 对命中范围必须通过 |
| `full` | 20–60 分钟 | 定期真实灾备演练；恢复算法、备份格式、信任链变化或真实恢复事故修复 | 不阻塞普通发布；仅上述四类变化是生产前硬门禁 |

时间是计划预算，不是强制超时。runner 是否继续只由结构化阶段、命令自身 timeout 和进程状态决定。`fast`、`specialized`、`full` 是叠加关系，不替代变更分类、VM Gate、签名 Gate、备份、迁移和生产验收。

`full` 建议至少每 30 天执行一次，记录上次时间、下次到期时间和实测 RTO。逾期对普通发布只告警；只有恢复算法、备份格式、信任链变化或真实恢复事故修复时，未通过当次 `full` 不得进入生产。

默认发布使用 `--recovery-gate-mode auto`，根据生产完整 commit、最终 diff 和 pending migration 分类。profile 白名单、版本、自测目录和入口兼容扩展经精确内容审阅后使用 `specialized`，仍执行真实生产快照的 VM 隔离恢复，不重复完整演练。审阅绑定同路径旧/新 Git blob 与文件模式；额外修改、删除或跨路径复用不得沿用。未知恢复关键变化标为 `full/recovery_change_requires_review`，在准备恢复包前阻断；显式 Full 参数不能绕过，也不会生成灾备证据。需要显式执行完整门禁的 VM 恢复部分时使用：

```text
python .agents/skills/sub2api-production-deploy/scripts/release.py deploy-follow --profile <profile> --commit <40位完整SHA> --mode blue-green|downtime --recovery-gate-mode full --lang zh-CN
```

该参数只绑定 `full` 分类并执行真实生产恢复包、旧镜像和隔离恢复检查，不表示生产级灾备故障注入、独立 `drill_id`、RTO 测量和演练收口已经完成；完整演练仍是单独的运维流程。

分类策略和只读身份解析修复可在精确内容审阅后登记 `reviewed_gate_policy_changed`，不能豁免恢复算法。生产容器按 digest 启动时，从该运行镜像的唯一完整 SHA 发布标签解析基线；身份缺失、标签冲突或 commit 不可证明则停止分类与发布，不按未知基线降级放行。

## Specialized 故障注入

### 完整灾备 Redis TTL 观测

真实生产快照的短 TTL 可能在恢复加载及健康延迟期间全部自然过期，不能强制要求真实 source 再现场出现一次惰性删除。完整灾备新版 Redis 测量同时增加严格的 `source_observation` 与 `boundary_probe`，旧格式继续原严格校验，未知或缺失字段拒绝。

真实 source 在同一 Lua 中读取 SCAN 前后 DBSIZE/expires，恢复输出使用 SCAN 后同刻计数；总键和 TTL 键减少量相等、永久键与备份精确相等，自然删除布尔如实记录，允许无 TTL 或没有自然删除。确定性边界另由同 Guest/engine、同真实 Redis image 的自有 network-none/tmpfs canary 证明：仅该容器关闭主动过期，永久键加 2000ms TTL 键，真实等待至少 2200ms 后观察 `2/1 -> 1/0`，永久 sentinel 摘要不变，删除后实际确认容器不存在。canary 明确非生产 source，绑定 drill/release/engine/rootfs/image，计数不得混入真实数据。

旧基线 schema-1 的 TTL 差值等式不放宽；完整灾备和候选签名、旧失败证据及信任根均保持独立。详见技能 [确定性 TTL 边界](../../.agents/skills/sub2api-production-deploy/references/backup-and-restore.md#完整灾备的确定性-ttl-边界)。

### Full DR 故障定位顺序

真实演练遇到失败时，先按阶段和同类问题做一次归因检查，再决定是否修复或重跑：

1. 先读取 release 的结构化阶段、退出码和固定 `reason_code`，确认 runner、Guest、source、镜像与身份是否仍属于同一 drill。
2. 再检查同一阶段的历史失败证据和当前输入 checksum，优先排查身份/recipient、隔离环境、解密、归档清单和权限/文件系统这几类重复故障。
3. 原始日志只在远端 root-only 目录做脱敏检索；不能把二次异常（例如测量文件缺失）当作首个 Guest 故障原因，也不能用补写 JSON 或复用旧 drill 掩盖失败。
4. 修改 helper 或恢复脚本后，必须提交新的完整 commit，重新生成 helper bundle、manifest、approval、drill 和 Gate；旧失败现场只保留为证据，不能在原 drill 内重跑。

## 幂等 checkpoint

协调恢复按以下语义阶段保存 checkpoint：

```text
compose_restored
postgres_restored
redis_restored
app_healthy
nginx_restored
backup_units_restored
state_cleanup
claim_reconciled
```

断线或进程退出后先复核现场。满足不变量的阶段直接跳过，状态矛盾则 fail-closed。业务已经恢复、只剩 cleanup 时，不得再次恢复数据库。

正式 helper 包通过完整 `release_asset_sha256` 原路径 map、完整 commit 与规范 JSON checksum 绑定，不按 basename 缩减原资产闭包。生产、协调恢复和隔离演练均从 `recovery-helpers/<sha>` 执行同字节 restore/finish/cleanup/reconcile，历史 claim 中旧脚本保持证据用途。恢复身份及逐阶段 started/done 保存在 release 目录，跨明文 cleanup 留存；未完成的数据写阶段仅允许完整现场证明后收养，不盲重放。先清明文、后释放 claim。

Redis 恢复的首次数据验真必须发生在应用启动前：恢复文件 checksum、RDB/AOF、认证与健康分别校验，总键和 TTL 键不超过备份，永久键下界不低于备份；惰性过期允许键数不同步下降，不采用精确差值等式。每次通过同一原子 Lua 采集 `DBSIZE`、`INFO keyspace` 与 `INFO server` 的 `run_id`，首次健康恢复保存 `redis.run-id.sha256`，以进程身份区分后续复验与重新启动。

Full DR 的惰性过期观测在同一 Lua 中先采 `before=DBSIZE`、`expires_before=INFO keyspace expires`，再实际 `SCAN` 并采 `after=DBSIZE`。三数仅针对 DB0，发现其他非空 DB 则阻断，不把全 DB 的 TTL 数与 DB0 总数混算。必须满足 `before > after >= 0`、`before >= expires_before >= 0` 和 `after >= before - expires_before`，证明实际删除过期键且永久键未丢失。不得用扫描后的总键数比较扫描前的 TTL 键数；Guest 收据与最终签名证据验证使用同一时点语义。正式 restore 的同快照校验与发布后 legacy 身份等式保持各自合同。

`app_healthy` 完成后，应用可合法增加或删除缓存，续跑不再比较恢复瞬间的键数上界与永久键下界；仍须复核健康、原子观测格式、checkpoint 与同一 `run_id` 摘要。重启或替换后的健康新实例不能冒充已验真的原恢复 Redis。复验失败保持阻断，不重灌 PostgreSQL/Redis。身份摘要、永久键基准及等待证据都在 checkpoint 白名单中，目录为 `root:root 0700`、文件为 `root:root 0400` 普通单链接，受 release/恢复点/旧 image/helper bundle 身份闭包约束，缺失或漂移不能自动补成成功。对应最低回归为 `test_redis_recovery_replay.py`，测试通过不代表真实 Full DR 或发布完成。

Compose 先快照完整选择文件与 `env_file/configs/secrets` 依赖，再复验拷贝和现场渲染与旧镜像一致，之后才可修改容器/数据库。宿主 Compose 选择/插值、Docker endpoint 不参与恢复；当前只支持同目录文件，`include`/`extends` 语义在写入前拒绝。Python 3 + PyYAML 与 Compose `--no-env-resolution` 是恢复运行前置能力。

隔离 Guest 的 Nginx include 闭包来自可信恢复来源 `nginx-T.txt`。`restore_nginx_include_closure` 按每个 `# configuration file` section 恢复原始字节，仅去掉 Nginx 添加的一个分隔 LF；写入前与单独归档的主配置、受管文件及 observability 配置逐字节交叉验证。include 目标只允许规范的 `/etc/nginx/` 受控根，重复 section、`..`、越界或 symlink 均拒绝；WebSocket map、MIME 等未单独归档的依赖也须保留来源原字节，不用 Guest 包默认数据或补造配置替换。runtime MIME 校验仍是前置检查；真实来源、生产恢复算法及严格 Nginx fingerprint 保持原样。最低回归为 `test_full_recovery_guest.py`；补齐 Guest 依赖不证明完整恢复或生产发布已通过。

Guest 包额外启用、但可信来源不存在的 module activation，仅在来源交叉核验与全部路径校验通过后清理。只允许 `modules-enabled/[数字]-mod-[名称].conf` symlink，且解析目标为同一 Guest 内 `usr/share/nginx/modules-available` 的普通文件；仅 `unlink` 激活链接，不删 module 二进制、package 配置或来源配置。来源已有 activation 保留，普通文件、未知命名、目录或链接目标越界均拒绝；最终 Nginx fingerprint 继续精确匹配来源。

专用 offline/private-user nspawn 演练复用正式包验证中断、Redis 等待和 TTL；合成 fixture、单元测试和 VM 渲染测试不能替代真实加密恢复。恢复算法变更的 full 生产硬门禁仍要求批准解密身份、真实资产、独立 drill、完整故障/耗时/checkpoint 证据及既有信任根签名。

### 真实 Redis 延迟观察的竞态收口

第二次 `restore.sh` 会先重新验证 PostgreSQL 全库 fingerprint，因此 Redis 的 150 秒启动观察预算必须从新写入的 `redis_restored.started` 开始，不能从观察线程启动开始计算。等待阶段标记使用独立的 1800 秒调用预算，整个 Guest 仍受执行器总时限约束；实际健康等待必须超过 60 秒且不超过已批准预算。缺少标记、启动过快、暂停或恢复失败均阻断，并记录稳定原因码与当前阶段。

真实 Guest 在 `redis_restored` 中断后，观察线程仍可能需要完成暂停窗口，`finish()` 先等待其有界收口；普通恢复异常或非预期退出则取消观察且保留原始恢复错误。惰性过期、应用中断/续跑/复验、清理中断/续跑/复验分别写子阶段，Guest 入口统一保存 root-only 脱敏失败标记。修复 helper 后重新生成 commit、bundle、授权和真实 DR，旧失败证据保持原样。旧无用测试资产按授权清理，必要阶段记录只暂存在 `.tmp`，部署验收后清理；不因暂存累积扩容。

### 宿主资源一致性与诊断

完整恢复演练前后严格比较宿主 Docker 资源身份集合，以及容器、卷和网络的选定元数据与进程身份。Docker `inspect` 的 `Mounts` 返回顺序不稳定，须先验证每项拥有唯一的字符串 `Destination`，再按该字段排序后散列完整条目；只消除同一挂载集合的展示顺序差异，不忽略 source、权限、传播模式或其他字段变化。配置中具有执行语义的数组保持原顺序，不能递归排序所有列表。缺失、重复或非法挂载目的地直接阻断。

### Guest 恢复运行时绑定

Guest Docker unit 使用 system containerd 的 `/run/containerd/containerd.sock`，离线镜像引用重建必须先核对 root-owned Unix socket、Docker `ExecStart` 的 `--containerd` 地址和 `moby` namespace。`ctr images inspect` 是人类可读输出，不能按 JSON 解析；执行器直接用 `ctr content get` 校验目标 OCI index、linux/amd64 manifest 与 config descriptor 的 SHA-256 链，再用 `docker image inspect` 核对原 Compose 引用的 image ID。禁止用当前 tag 猜测旧摘要、拉取镜像或忽略摘要不匹配。

Guest Nginx 配置闭包之外的运行依赖也属于恢复前置：新 rootfs 从已批准 rootfs 运行数据恢复 `/etc/nginx/mime.types`，绑定固定字节数与 SHA-256（3957 bytes，`632f37cafbdce8ebfba27f7d8264da1ea462880c4961c32354455c8ab722f7c3`），并以 root `0644`、普通单链接、非空文件验真；摘要不代替未取得的 dpkg 来源证明。随后才覆盖捕获的生产 Nginx 配置、执行 `nginx -t` 和启动服务。缺失或来源漂移保持 blocked，不能复制宿主其他软件的同名文件。

### Shell 必需断言与失败传播

发布、恢复与清理入口不能只依赖 `set -e`：独立的 `! command`、非末项 `test A && test B`、条件上下文调用的函数，以及命令替换或进程替换内的失败，都可能被后继成功覆盖。必需断言逐项执行；条件调用的函数显式传递每步失败，或使用独立严格 Bash 进程。删除与停机必须在查询成功后再判断精确资源不存在，查询失败不能当作零数量；计数只在实际删除并独立读回确认后增加。

命令输出与退出状态分别验真。`test "$(command)" = expected` 会忽略 command 的非零状态，必需采集先独立赋值并核验退出码，再检查内容。允许的无匹配与采集错误分开处理；生产日志查询失败不能报告 logs pass。Nginx 配置冲突或查询失败须进入已有事务回滚，不能直接退出而跳过 ERR trap。

systemctl 查询按输出和退出码的组合识别状态，例如 `active/0`、`inactive/3`、`failed/3`、`masked/1`；其余组合保持未知并阻断动作，不能把任意非零退出当作 inactive。备份单元 mask/restore 与回滚的验证使用相同边界。隔离恢复入口的 source、Compose 加载及最终摘要在独立严格 Bash 主流程执行，前置步骤失败不得被后续成功掩盖；VM 下载清单中任一链接失败也不能发布 ready 标记。

回归从正式调用上下文注入失败，覆盖前置对象、元数据采集、事务每步、回滚失败、非末项 source 断言、清理命令替换和后置读回；使用无害 stub，不接触真实生产资源。所有同族补丁与交叉审阅固定后才生成新 helper、授权、DR、Gate 和 release，保留旧失败证据。
