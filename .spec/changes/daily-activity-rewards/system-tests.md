# daily-activity-rewards 系统测试

## 测试环境

- runtime/platform：本地 Go 测试数据库/Redis fixture，前端 Vitest；时区固定 `Asia/Shanghai`。
- fixture/data：用户、邀请关系、已结算/失败/退款充值订单、成功消费事件、活动配置和重复 webhook 事件。
- 外部依赖：支付与余额服务使用 mock；禁止真实生产支付、邮件、上游请求或外部活动接口。

## ST-01 用户查看活动与进度

- 类型：normal
- 前置：活动开启；用户今日成功充值 10 元、消费 50 元，有 3 个达标邀请和 1 个充值机会。
- 操作：打开 `/activities/daily`，读取 summary 和奖励列表。
- 断言：显示中国时区活动日、礼包可领、充值/消费进度、邀请 `3 / 5`、永久机会；入口位于邀请返利下方。
- 证据：相关 handler/service 测试与 `DailyActivitiesView` Vitest 输出。

## ST-02 礼包与抽奖成功入账

- 类型：normal
- 前置：用户满足礼包门槛，拥有充值/消费/邀请机会。
- 操作：领取礼包并分别抽取一次；使用随机 fixture。
- 断言：奖励金额分别落在配置区间，机会只扣一次，奖励记录、余额流水和 summary 一致。
- 证据：活动 service 集成测试、余额 repository fixture。

## ST-03 重复提交与并发领取

- 类型：failure
- 前置：同一用户同时发送相同幂等键的礼包/抽奖请求。
- 操作：并发提交并在余额入账 mock 中注入重试。
- 断言：每日礼包只成功一次；同一机会只产生一条奖励；重复请求返回原结果或明确已处理，无双重扣减/发奖。
- 证据：事务/幂等测试与数据库唯一约束断言。

## ST-04 邀请达标永久累计

- 类型：normal
- 前置：同一邀请人有 5 个不同被邀请用户，各自在成功结算充值累计达到 10 元。
- 操作：处理支付履约事件，重复投递其中一个事件，再打开活动页并抽奖。
- 断言：只产生 5 次达标计数和 1 个永久邀请机会；后续充值、重复事件不再增加；奖励金额为 5～10 元。
- 证据：邀请 milestone/机会集成测试。

## ST-05 充值来源口径、去重与每日边界

- 类型：boundary
- 前置：余额/订阅成功订单、失败/取消/退款订单、正数余额兑换码、支付自动兑换码、并发/订阅/负数兑换码，以及管理员 add/set/subtract 分别跨越北京时间 00:00；管理员充值返利开关覆盖开/关两种状态；存在昨日永久机会。
- 操作：执行进度聚合并读取 summary。
- 断言：余额/订阅成功订单和正数余额兑换码进入当日进度；支付自动兑换码不重复；仅开关开启时发生的正数管理员 add 计入，set/subtract 不计入；其它失败或非余额来源均排除；昨日机会仍可用，当天礼包状态按新活动日重新计算。
- 证据：时区边界与事件过滤测试。

## ST-06 非法客户端输入 fail closed

- 类型：failure
- 前置：已认证用户。
- 操作：提交伪造金额、门槛、中奖金额、他人 user ID、未知 activity type、负数/超大 count。
- 断言：请求拒绝或忽略伪造字段；不产生机会扣减、奖励、余额流水或跨用户数据访问。
- 证据：handler contract tests。

## ST-07 配置审计和硬上限

- 类型：boundary
- 前置：管理员打开活动设置。
- 操作：保存合法配置，再保存负数、NaN、最小值大于最大值、0 门槛、超上限和非整数邀请次数。
- 断言：合法配置生成新规则版本和审计记录；非法配置原子拒绝且旧配置不变。
- 证据：settings handler/service tests。

## ST-08 现有邀请返利隔离

- 类型：normal
- 前置：邀请人存在现有返利流水和独立活动达标记录。
- 操作：查看活动与返利页面并完成一次活动抽奖。
- 断言：活动奖励只写活动奖励/余额流水，不增加返利配额、返利冻结额或返利流水；原返利功能仍可用。
- 证据：affiliate regression tests 和活动账本查询断言。
